# Specification

**Status:** stable · **Version:** 2.4 · **Supersedes:** LOCK v1.0 (adaptor
signatures), v1.1 (Proof-of-Access)

This page is the normative OC Lock specification. Where this document and the
[reference SDK](https://github.com/orangecheck/oc-packages) disagree, this
document wins.

## §0 Notation

- Bytes are lowercase hex unless marked `base64url`.
- `||` denotes byte concatenation.
- `KDF()` is HKDF-SHA256 per RFC 5869.
- `AEAD()` is AES-256-GCM per NIST SP 800-38D (12-byte IV, 16-byte tag).
- `ECDH(k, P)` is X25519 per RFC 7748 (output 32 bytes).
- `BIP322(addr, msg)` is a BIP-322 signature, encoded as base64.
- Canonical JSON is UTF-8, lexicographically-sorted keys, no insignificant
  whitespace, LF-terminated. See §5.

## §1 Actors

- **Sender** — the party creating a vault.
- **Recipient** — the party able to unseal the vault.
- **Device** — a browser or app instance holding a device keypair bound to a
  Bitcoin identity.
- **Directory** — a Nostr relay (or set of relays) storing device records.
- **Relay (optional)** — a server holding payment-gated content keys, releasing
  them upon observing qualifying Bitcoin payments.

Sender and recipient may be the same person (self-vault).

## §2 Identities

An **OC identity** is the pair `(btc_address, attestation_id)` where:

- `btc_address` is a mainnet Bitcoin address (P2WPKH, P2TR, or P2PKH)
- `attestation_id` is the SHA-256 of a canonical orangecheck message signed by
  that address

A recipient MUST have an OC identity known to the sender. OC Lock does not
publish recipient pubkeys; it publishes **device keys** addressable by the
recipient's Bitcoin address.

## §3 Device keys

A **device key** is a long-lived X25519 keypair generated by a recipient in a
particular client and bound to their Bitcoin identity by a BIP-322 signature.

### §3.1 Generation

```
(device_sk, device_pk) := x25519_keygen()
```

`device_sk` MUST be stored in a confidential local store (IndexedDB with
`extractable=false` via WebCrypto if available, else plaintext). `device_sk`
MUST NOT leave the device.

### §3.2 Binding statement

```
oc-lock:device-bind:v3
address: <btc_address>
device_pk: <hex(device_pk)>
nostr_pk: <hex(nostr_pk), x-only, lowercase>
device_id: <random 16-byte hex>
created_at: <iso8601 utc>
```

Each line terminated with LF (`\n`).
`binding_sig = BIP322(btc_address, binding_statement)`.

Publishers MUST emit v3. A verifier MUST reject a v3 record whose `event.pubkey`
differs from the signed `nostr_pk`. Readers still accept v2 records, which lack
the `nostr_pk` line, for sealing to `device_pk`; from 2027-01-21 a v2 record
names no inbox key (§3.4).

### §3.3 Publication

Published as a Nostr addressable event (kind `30078`):

```
kind:       30078
tags:       [
  ["d",           "oc-lock:device:<btc_address>"],
  ["addr",        "<btc_address>"],
  ["device_id",   "<device_id>"],
  ["device_pk",   "<hex(device_pk)>"],
  ["alg",         "x25519"],
  ["binding_sig", "<base64(binding_sig)>"]
]
content:    <exact bytes of binding_statement>
pubkey:     <ephemeral nostr pubkey, see §3.4>
created_at: <unix seconds>
```

A client SHOULD keep publishing a device record, a bind or a revocation until at
least two of the relays readers ask, each asked alone, serve back a copy that
verifies, or every one of them does when readers ask fewer than two, and SHOULD
NOT report the device as set up, or as revoked, until then.

### §3.4 Nostr authorship

The Nostr `pubkey` isn't tied to the Bitcoin identity — authenticity is the
BIP-322 `binding_sig`. A fresh ephemeral Nostr keypair SHOULD be derived
deterministically from the device secret:

```
nostr_sk := HKDF(ikm=device_sk, salt="oc-lock/v2/nostr-key", info="nostr-sk", L=32)
```

**Which key is a device's inbox.** A v3 record authorizes its signed `nostr_pk`.
From **2027-01-21T00:00:00Z** by the verifier's clock, a v2 record authorizes no
Nostr key. Before then, a v2 record authorizes its `event.pubkey` only while no
v3 record of the same device exists and exactly one key carries it. A v2 bind
stays live for sealing to `device_pk`, so a device whose binds are all v2 still
receives envelopes, by link rather than at a Nostr inbox.

**Re-binding a v2 device.** A client holding a live v2 device's secret SHOULD
publish a v3 statement for the same address, `device_id` and `device_pk`, under
the key derived from the device secret. The re-bind MUST carry the v2
statement's `created_at`, so a revocation of the device retires it too. A client
SHOULD offer the re-bind for its own v2 devices and say when v2 stops naming an
inbox.

### §3.5 Rotation and revocation

A device stops receiving new envelopes only through a **revocation**: a
kind-30078 event with `device_pk = "revoked"`, whose content is this statement
and whose `binding_sig` is the address's BIP-322 signature over it.

```
oc-lock:device-revoke:v2
address: <btc_address>
device_id: <device_id>
revoked_at: <iso8601 utc>
```

Every line ends in LF, the last one too. File it under `oc-lock:device:<addr>`,
which every reader queries. A device revoking itself should carry it under its
own Nostr key, so that every relay that accepts it stops serving that device's
bind; it may use a fresh key. Carry a revocation of another device with a fresh
key. Never carry one with a key that carries another live bind of the address:
relays replace a record by `(pubkey, kind, d)`, so it would take that bind's
place. Readers accept it under any key. The authority is the address's
signature, so a lost device can be revoked with the wallet alone. A reader takes
the revocation's address and `device_id` from its signed statement, and does not
reject one whose `binding_sig` verifies because its `addr`, `device_id` or
`device_pk` tag is missing or says something else, or because of its `d` tag.

**Which binds are live.** Collect the device records for the address from every
relay you queried and drop each one whose `binding_sig` does not verify. Before
merging what the relays returned, verify each event under NIP-01 and drop one
that fails; that checks the Nostr wrapper, never which key carries the record. A
bind of `(address, device_id)` is live unless a remaining revocation of that
pair has a signed `revoked_at` at or after the bind's signed `created_at`. That
holds whichever Nostr key carried each record and whichever relay served it, so
a revocation one relay holds retires the bind another relay still serves.
`event.created_at` orders nothing. A revocation that verifies but signs no
readable `revoked_at` retires every bind of its device, whatever that bind's
`created_at`. A revocation whose signature does not verify retires nothing. A
bind whose signed `created_at` is later than the reader's clock plus a skew
allowance (10 minutes recommended) is not live yet; list it anyway, so it can be
revoked.

**A revocation's absence needs the read floor.** Page each relay's answer for
the address with `until` until a page comes back shorter than the `limit` you
asked for; a relay whose read stopped at a full page, or that stopped answering,
was cut off. The absence of a revocation counts only when the read floor of the
relays queried answered in full: the number queried, less the write quorum of 2,
plus one, and never fewer than one (four of five). While any relay queried was
cut off it does not count at all: the result is unchecked, never "no
revocation". A sender without the floor, or with any relay cut off, MUST NOT
seal, and reports `E_RELAY_UNREACHABLE`.

Conforming senders MUST seal only to live binds, and report `E_REVOKED` when
none is left.

**Dating a revocation.** Sign `revoked_at` no earlier than your clock and no
earlier than the latest signed `created_at` among that device's binds you hold,
so the revocation retires a bind dated ahead too. Read the device's records
again before you report it revoked.

- **Rotate** — bind a new device under a new `device_id`, then revoke the old
  one. The new record does not replace the old: each device publishes under its
  own Nostr key, so the two sit at different NIP-33 coordinates.

### §3.6 Multi-device

Each device publishes its record under its own Nostr key at
`oc-lock:device:<addr>`, so the records stay apart by `pubkey`. New records
should use that form. The per-device form `oc-lock:device:<addr>:<device_id>`
stays valid, but a `#d` query for the address does not return it. Senders
encrypt once per live device (§3.5).

## §4 Envelope format

A sealed vault is a canonical JSON object. File extension `.lock`, MIME
`application/vnd.oc-lock+json`.

### §4.1 Schema

```json
{
  "v": 2,
  "kind": "identity" | "payment",
  "id": "<32-byte hex>",
  "alg": { "kem": "x25519", "aead": "aes-256-gcm", "kdf": "hkdf-sha256" },
  "from": {
    "address": "<btc address>",
    "attestation_id": "<sha256 of sender's OC message, optional>"
  },
  "recipients": [
    {
      "address":     "<btc address>",
      "device_id":   "<recipient device id>",
      "device_pk":   "<hex X25519 pubkey>",
      "eph_pk":      "<hex X25519 ephemeral pubkey>",
      "wrapped_key": "<base64url(AEAD(content_key, kek, nonce_kek))>",
      "nonce_kek":   "<12-byte hex>"
    }
  ],
  "ciphertext": "<base64url(AEAD(payload, content_key, nonce_ct))>",
  "nonce_ct":   "<12-byte hex>",
  "hint":       "<optional plaintext hint, <= 200 bytes>",
  "created_at": "<iso8601 utc>",
  "expires_at": "<iso8601 utc | null>",
  "payment":    null | { "amount_sats": <int>, "address": "<btc addr>", "confirmations": <int>, "relay": "<url>" },
  "sig": { "alg": "bip322", "pubkey": "<sender btc address>", "value": "<base64 sig>" }
}
```

### §4.2 Encryption (identity mode)

1. Generate random `content_key` (32 bytes).
2. Generate random `nonce_ct` (12 bytes).
3. `ciphertext = AEAD(content_key, nonce_ct, payload, aad=envelope_id_draft)`
   where `envelope_id_draft` is SHA-256 of the canonical envelope with
   `ciphertext`, `sig`, and `recipients[*].wrapped_key` elided.
4. For each recipient device:
    - `(eph_sk, eph_pk) := x25519_keygen()`
    - `shared = X25519(eph_sk, device_pk)`
    - `kek = HKDF(shared, salt=nonce_ct, info="oc-lock/v2/kek:" || device_id, L=32)`
    - `nonce_kek` random 12 bytes
    - `wrapped_key = AEAD(kek, nonce_kek, content_key, aad=device_id)`
    - zeroize `eph_sk`
5. Canonicalize full envelope; `id = sha256(canonical_bytes_without_sig)`.
6. `sig.value = BIP322(sender_addr, id)`.
7. Zeroize `content_key`.

### §4.3 Decryption (identity mode)

1. Recompute `id`. Reject on mismatch.
2. Verify `sig.value` against `id` using BIP-322. (Clients MAY skip for
   self-seals.)
3. Find recipient entry matching local `device_id`. If none — `E_NOT_ADDRESSED`.
4. `shared = X25519(device_sk, eph_pk)`.
5. `kek = HKDF(shared, salt=nonce_ct, info="oc-lock/v2/kek:" || device_id, L=32)`.
6. `content_key = AEAD.decrypt(kek, nonce_kek, wrapped_key, aad=device_id)`.
7. `payload = AEAD.decrypt(content_key, nonce_ct, ciphertext, aad=envelope_id_draft)`.
8. Zeroize `shared`, `kek`, `content_key`.

### §4.4 Payment mode

Replaces step 4 in §4.2 with a single "recipient" that is the named relay. The
unseal flow requires the recipient to authenticate to the relay (via orangecheck
sign-in) and submit a confirmed payment tx; the relay then unwraps the content
key and re-wraps for the recipient's device.

The relay is a trust anchor. Clients MUST display the relay URL prominently
before accepting payment-mode vaults.

## §5 Canonicalization

- UTF-8 JSON with keys sorted lexicographically at every level.
- No insignificant whitespace.
- Arrays preserve order. Within `recipients[]`, entries MUST be sorted by
  `device_id` ascending.
- Numbers: integers within IEEE 754 double range without fractional zeros or
  exponents.
- Strings: `\uXXXX` only for control chars and `"` / `\`.
- Final byte is LF.

Reference: RFC 8785 JCS, with the additional `recipients[]` rule.

## §6 Errors

| Code                  | Meaning                                                     |
| --------------------- | ----------------------------------------------------------- |
| `E_NO_DEVICE`         | No device key found for this browser.                       |
| `E_NOT_ADDRESSED`     | Envelope does not include the recipient's `device_id`.      |
| `E_BAD_SIG`           | Sender BIP-322 signature did not verify.                    |
| `E_BAD_TAG`           | AEAD authentication failed (tampered or wrong key).         |
| `E_EXPIRED`           | `expires_at` is in the past.                                |
| `E_REVOKED`           | No device record for the address is live (§3.5).            |
| `E_PAYMENT_UNMET`     | Relay could not verify required payment.                    |
| `E_RELAY_UNREACHABLE` | Too few relays answered in full, or one was cut off (§3.5). |

## §7 Security model

**Proves:**

- Authenticity (sender's BIP-322 signature over envelope id)
- Confidentiality (only holders of a listed `device_sk` can derive the content
  key)
- Identity binding (recipient's `device_pk` bound to `btc_address` by BIP-322)

**Does NOT prove:**

- Order / freshness — `created_at` is informational only.
- Delivery — transport is your problem.
- Metadata privacy — `from.address`, `recipients[*].address`, `hint`,
  `payment.address` are plaintext.

**Trust assumptions:**

- Identity mode: trustless. Nostr relays can censor but cannot forge.
- Payment mode: explicit trust in the named relay.

## §8 Versioning

`v` is an integer. Clients MUST reject envelopes whose `v` they don't support.
Minor additions handled via unknown-field tolerance.

## §9 Compliance checklist

A client is OC Lock v2 compliant iff:

- Generates device keys as X25519, stores `device_sk` non-extractable when
  WebCrypto permits.
- Produces binding statements byte-for-byte per §3.2.
- Publishes kind-30078 records per §3.3 with BIP-322 binding signature.
- Canonicalizes envelopes per §5 — identical `id` across implementations.
- Accepts and produces all required envelope fields per §4.1.
- Verifies sender BIP-322 signatures before accepting envelope contents.
- Seals only to live binds: applies every revocation whose BIP-322 signature
  verifies, from any relay and any Nostr key, by signed timestamps (§3.5).
- Files a revocation it publishes under `oc-lock:device:<addr>`: a
  self-revocation under the device's own key, a revocation of another device
  under a fresh key, never under a key that carries another live bind (§3.5).
- Enforces `expires_at` when present.
- Emits error codes per §6.

## §10 External identifiers

- Nostr kind: `30078` (addressable). `d`-tag namespace `oc-lock:device:*`
  claimed by this spec.
- File extension: `.lock`
- MIME: `application/vnd.oc-lock+json` (self-allocated)
